====================================================================== 1.
PURPOSE AND EXPECTED OUTCOME
======================================================================

Build the engineering foundation for ATLAS, a production-oriented,
multi-agent research and retrieval-augmented generation (RAG) platform.

ATLAS MUST use a microservices architecture. Do not create one large
FastAPI application that contains all business capabilities.

For Phase 1, create a clean monorepo, independent service scaffolds,
shared contracts and utilities, centralized configuration conventions,
structured logging, health endpoints, tests, and local development
instructions.

Phase 1 is infrastructure and application scaffolding only. Do not
implement actual RAG, embeddings, vector search, LLM agents, document
ingestion logic, research workflows, or production database integration
in this phase.

The result must run on Windows using PowerShell 5.1 and Python 3.12.6.
Docker is not currently installed on the developer’s machine. Do not
make Docker a blocker for Phase 1. Services must be runnable locally
using separate Python processes and virtual environments. Add Docker
readiness files only if they can be added without requiring Docker to
run the project.

3. ARCHITECTURAL DECISIONS
======================================================================

Architecture: - Microservices. - Monorepo for source control and
coordinated development. - Each service owns its API, application logic,
domain logic, infrastructure adapters, configuration, tests, and runtime
entrypoint. - Services must be independently startable as separate
processes. - Services communicate through explicit versioned
contracts. - Use synchronous HTTP for simple request/response
communication in the initial foundation. - Asynchronous messaging will
be introduced in a later infrastructure phase when the actual workflows
and event boundaries are defined. - Do not introduce service-to-service
calls unnecessarily in Phase 1.

Initial service boundaries:

1.  api_gateway External API entry point. Future responsibility:
    routing, request validation, authentication integration, rate
    limiting and API versioning. In Phase 1 it only needs a minimal
    FastAPI application and health route.

2.  research_orchestrator Future responsibility: create and coordinate
    research jobs, manage workflow state, and coordinate the agent
    runtime. In Phase 1 it only needs a minimal service scaffold and
    health route.

3.  ingestion_service Future responsibility: accept documents and URLs,
    extract text, normalize content, chunk documents, and initiate
    indexing. In Phase 1 it only needs a minimal service scaffold and
    health route.

4.  retrieval_service Future responsibility: keyword, vector and hybrid
    retrieval, filtering, reranking and retrieval result normalization.
    In Phase 1 it only needs a minimal service scaffold and health
    route.

5.  agent_runtime Future responsibility: execute logical agents such as
    Researcher, Analyst, Verifier and Synthesizer. These are logical
    agents within this service initially, NOT separate microservices in
    Phase 1. In Phase 1 it only needs a minimal service scaffold and
    health route.

6.  evaluation_service Future responsibility: evaluate retrieval
    quality, answer quality, citation correctness, groundedness and
    regression performance. In Phase 1 it only needs a minimal service
    scaffold and health route.

Shared packages:

-   shared/contracts: versioned request/response schemas and event
    contracts.
-   shared/common: small, stable cross-service primitives only.
-   shared/observability: correlation ID and logging conventions.
-   shared/security: reserved for shared security interfaces and
    helpers. Do not build a custom authentication system in Phase 1.

Infrastructure folder:

-   infrastructure/docker: future Dockerfiles and container-related
    assets.
-   infrastructure/scripts: developer and maintenance scripts.
-   Do not require Docker Compose for the local Phase 1 run.

IMPORTANT: Do not create a distributed monolith. Do not put all business
logic in shared/common. Shared packages must contain only genuinely
reusable cross-service code. Each service must own its business logic
and data access logic. Avoid shared database models across services.

6. CONFIGURATION REQUIREMENTS
======================================================================

Each service must own its configuration.

Use Pydantic Settings. Configuration must come from environment
variables and an optional local .env file. Do not hardcode hostnames,
credentials, API keys, database URLs or machine-specific paths.

Each service’s configuration should include, as appropriate:

-   SERVICE_NAME
-   SERVICE_VERSION
-   ENVIRONMENT (local, test, staging, production)
-   HOST
-   PORT
-   LOG_LEVEL
-   LOG_FORMAT (json or console)
-   API_PREFIX

Provide safe defaults for local development.

Never commit real .env files. Commit .env.example files with placeholder
values only.

Do not create one global settings object that imports every service’s
settings. A service must load only its own settings.

Validate settings at application startup. Invalid configuration should
produce a clear error without exposing secrets.

7. LOGGING AND CORRELATION ID
======================================================================

Implement a small reusable observability package.

Requirements:

-   Use Python logging, not print statements.
-   Support readable console logs for local Windows development.
-   Support JSON structured logs for machine processing.
-   Include timestamp, severity, service name, logger name and message.
-   Include correlation_id when available.
-   Never log secrets, authorization headers, API keys or full sensitive
    document content.
-   Provide a correlation ID middleware for each FastAPI service.
-   If an incoming X-Correlation-ID header exists and is valid, preserve
    it.
-   Otherwise generate a UUID.
-   Return X-Correlation-ID in the response.
-   Keep middleware implementation small and tested.
-   Do not add OpenTelemetry yet unless the phase explicitly requires
    it.

The shared observability package should expose a documented setup
function and correlation context utilities. Avoid circular imports.

8. SERVICE APPLICATION REQUIREMENTS
======================================================================

Each of the six services must have:

-   A package entrypoint.
-   A FastAPI app factory or a clearly testable app construction
    function.
-   A /health/live endpoint.
-   A /health/ready endpoint.
-   A service identity response including service name and version.
-   Configuration validation.
-   Structured logging.
-   Correlation ID middleware.
-   Unit tests for the health routes and configuration behavior.

Liveness: - Indicates that the process and application event loop are
alive. - Must not fail because a future database or vector store is
unavailable.

Readiness: - In Phase 1, indicates that the service has completed
startup and can accept requests. - Do not pretend external dependencies
are healthy when they are not configured. - As dependencies are
introduced in later phases, readiness checks can include them with
explicit timeout and status reporting.

Health response should be consistent across services. Example shape:

    {
      "status": "ok",
      "service": "ingestion-service",
      "version": "0.1.0"
    }

For readiness, a response may include:

    {
      "status": "ready",
      "service": "ingestion-service",
      "version": "0.1.0",
      "checks": {}
    }

Use shared response contracts only if that does not create unnecessary
coupling. Keep the API response versioned and documented.

======================================================================

The API Gateway is the only externally exposed entry point in the
intended architecture.

For Phase 1: - Create its FastAPI application. - Add its own health

Document that later service routing will be configured explicitly.

Each internal service should listen on its own local port during
development. Bind to 127.0.0.1 by default for local development unless
there is a specific reason to expose it on the network.

Suggested local ports:

-   API Gateway: 8000
-   Research Orchestrator: 8001
-   Ingestion Service: 8002
-   Retrieval Service: 8003
-   Agent Runtime: 8004
-   Evaluation Service: 8005

Make ports configurable using environment variables. Avoid port values
being duplicated in unrelated code. Document the local port map.

13. SECURITY AND QUALITY RULES
======================================================================

-   Never commit .env files or secrets.
-   Add .env, .venv, pycache, .pytest_cache, .ruff_cache, logs, coverage
    outputs and local artifacts to .gitignore.
-   Do not hardcode user-specific Windows paths in application code.
-   Use pathlib for filesystem paths.
-   Use type hints.
-   Keep functions and classes focused.
-   Avoid giant files and giant configuration modules.
-   Avoid wildcard imports.
-   Avoid circular imports.
-   Avoid global mutable state.
-   Do not use print for application logging.
-   Do not suppress exceptions silently.
-   Do not catch Exception unless there is a clear boundary and the
    exception is logged and translated appropriately.
-   Do not expose stack traces or internal errors in API responses.
-   Keep secrets out of logs and test snapshots.
-   Add docstrings to public interfaces where useful.
-   Prefer explicit dependency injection over hidden global
    dependencies.
-   Do not create abstractions without a real Phase 1 use case.

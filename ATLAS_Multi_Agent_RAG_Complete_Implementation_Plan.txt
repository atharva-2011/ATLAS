Executive overview ATLAS is a production-oriented Multi-Agent
Retrieval-Augmented Generation (RAG) system for research. It combines
agent orchestration with two knowledge acquisition paths: internal
document retrieval and external research. Agents specialize in planning,
source discovery, domain analysis, verification, critique and synthesis.
The system is designed for complex, multi-part questions where one
retrieval call and one LLM response are not sufficient. The supervisor
coordinates the workflow, while every agent works within a defined
responsibility and returns structured findings with source provenance.
What ATLAS will do ● Interpret a research question and identify scope,
constraints, time horizon and expected output. ● Break the question into
research tasks and assign work to suitable agents. ● Search uploaded
documents and external sources using fit-for-purpose retrieval tools. ●
Use hybrid retrieval (dense semantic search plus sparse keyword search)
and reranking where appropriate. ● Normalize findings into evidence
records with source, location, date and retrieval metadata. ● Verify
whether sources actually support claims and flag contradictions or weak
evidence. ● Run a critic pass to identify gaps, unsupported conclusions
and missing perspectives. ● Produce a structured report with citations,
limitations and a traceable evidence trail. ● Persist research runs,
tasks, agent executions and artifacts so work can be inspected and
resumed. Non-goals for the first release ● The system will not
autonomously publish research or take consequential external actions. ●
It will not treat LLM-generated confidence as a calibrated probability.
● It will not assume that more agents automatically mean better
research. ● It will not treat retrieved web pages or uploaded files as
instructions for the agents. ● It will not claim exhaustive coverage of
the web or of any literature corpus. Design principle: use the smallest
number of agents that reliably completes the task. Parallelize
independent research tasks, but keep shared state, evidence contracts
and quality gates explicit. 2. Target use case and example Example user
request “Research the adoption of Generative AI in healthcare. Analyze
applications, market trends, technical developments, regulatory
considerations, risks and future opportunities. Provide evidence-backed
findings with citations and clearly identify uncertainty.”

End-to-end workflow Step Action Decision / output 1. Intake Validate
question, scope, dates, requested depth and available files. Research
request accepted or rejected with validation errors. 2. Plan Planner
creates research dimensions, subtasks, source requirements and success
criteria. Structured plan with task IDs and dependencies. 3. Route
Supervisor assigns tasks to internal-document or external-research
agents. Agent assignments and tool permissions. 4. Retrieve Agents
search, fetch and extract relevant material. Candidate source records
and passages. 5. Analyze Agents produce concise findings linked to
evidence IDs. Structured findings, not free-floating prose. 6. Verify
Verifier checks each material claim against its cited evidence.
Supported, partially supported, contradicted or unsupported. 7. Critique
Critic checks coverage, diversity, contradictions and unanswered tasks.
Gap list and revision recommendations. 8. Revise Supervisor selectively
reopens tasks if budget and retry limits allow. Additional evidence or
explicit unresolved gaps. 9. Synthe size Synthesizer writes report from
validated findings. Report with inline citations and reference list. 10.
Persist Save report, sources, task outcomes and execution trace.
Retrievable research record. 4.2 Conditional routing rules ● If the
request is simple and narrow, use a compact retrieval-and-answer path
rather than launching multiple agents. ● If internal files are attached
or selected, route relevant tasks to the document researcher. ● If
current or time-sensitive facts are requested, use external research and
record publication and retrieval dates. ● If evidence is insufficient,
allow a bounded retrieval retry with a rewritten query or a different
source type. ● If claims conflict, preserve both positions and report
the disagreement rather than forcing a false consensus. ● If retry
budget is exhausted, synthesize with an explicit limitations section or
mark the run incomplete.

Retrieval and knowledge architecture Research RAG needs two distinct
ingestion and retrieval paths. They converge into a common evidence
model so downstream agents can reason over consistent records without
losing provenance. 5.1 Internal document RAG Stage Implementation
responsibility Upload Validate file type, size, tenant ownership and
malware scanning policy. Extraction Extract text, page numbers, tables
and document metadata; preserve page-level locations. Normalization
Clean extraction artifacts while retaining original text and source
coordinates. Chunking Split by document structure first, then enforce
token/character limits with overlap. Embedding Generate vectors using a
configured embedding model and version. Indexing Store vectors and
metadata in Qdrant; maintain sparse index for keyword retrieval.
Retrieval Apply tenant and document ACL filters before returning
candidate chunks. Reranking Rerank candidates using a CrossEncoder or
another evaluated reranker. Evidence capture Store exact passage,
page/section, document ID and content hash. 5.2 External research path
Stage Implementation responsibility Query generation Create focused
search queries from a research task. Search Call a search provider
through an adapter with rate limits and timeouts. Fetch Fetch allowed
pages or source records; respect provider terms and robots/access rules.
Extraction Extract title, author/publisher, date, canonical URL and
relevant passages. Quality checks Deduplicate, classify source type and
flag missing or ambiguous dates. Evidence capture Store source snapshot
metadata and passage references; preserve URL and retrieval time. 5.3
Hybrid retrieval Use dense retrieval for semantic similarity and sparse
retrieval for exact terms, acronyms, names, model numbers and phrases.
Combine candidates, deduplicate them, then rerank. The exact fusion
strategy and top-k values must be selected through evaluation, not
guessed. Retrieval method Strength Typical weakness Dense vector search
Finds semantically related passages even when wording differs. Can miss
exact identifiers, rare terms or precise phrases. Sparse / BM25 Strong
for exact words, names, acronyms and technical terms. May miss
semantically equivalent wording. Hybrid fusion Combines complementary
signals. Needs tuning and careful deduplication.

Chunking and metadata recommendations ● Prefer structure-aware chunking:
headings, paragraphs, tables, abstracts and sections. ● Store document
ID, tenant ID, page number, section heading, source type, publication
date and embedding version. ● Use stable chunk IDs and content hashes to
support deduplication and re-indexing. ● Avoid excessively small chunks
that lose context and excessively large chunks that dilute retrieval. ●
Keep original documents in object storage and extracted text/metadata in
durable storage. ● Apply access-control filters before retrieval, not
after the model has seen the content.

Agent contracts and orchestration LangGraph should coordinate agents
through typed state and explicit node outputs. The state is a workflow
contract, not a dumping ground for entire documents or long chat
transcripts. 6.1 Shared state design class ResearchState(TypedDict):
research_id: str user_query: str scope: dict plan: dict tasks:
list[dict] task_results: Annotated[list[dict], operator.add]
evidence_records: Annotated[list[dict], operator.add] verified_claims:
list[dict] rejected_claims: list[dict] gaps: list[dict] critique: dict
report: dict | None retry_count: int status: str errors: list[dict] Use
reducers for fields that receive parallel updates. Do not let multiple
nodes overwrite the same list without a defined merge strategy. Store
large payloads in PostgreSQL or object storage and pass IDs or compact
summaries through graph state. 6.2 Agent input/output contract Contract
field Purpose agent_id Stable identity of the agent implementation.
task_id Research task being executed. objective Specific question the
agent must answer. allowed_tools Explicit list of tools the agent may
use. source_scope Allowed internal collections, tenant scope or external
domains. output_schema Pydantic schema defining required output fields.
evidence_ids References to evidence records supporting findings. status
Succeeded, partial, failed or skipped. usage Token, latency and
tool-call accounting. 6.3 Supervisor responsibilities ● Create the plan
and validate that tasks are sufficiently specific. ● Choose which agents
are necessary and which tasks can run in parallel. ● Enforce maximum
parallel tasks, timeouts, retry budgets and token/cost budgets. ● Track
task status and checkpoint state for recovery. ● Route weak or
conflicting evidence to targeted follow-up research. ● Prevent synthesis
until required verification and quality checks have completed. ● Persist
execution events and produce a final run status. 6.4 Parallelism and
dependencies Independent research tasks can run in parallel. Tasks that
depend on earlier findings should be sequenced. For example, the planner
must complete before task fan-out; evidence verification must follow
evidence collection; synthesis must follow verification and critique.

Production reliability, security and governance Research systems process
untrusted content and can invoke external tools. Treat source text as
data, enforce permissions outside the LLM, and make execution bounded
and observable. 8.1 Security controls Risk Control Prompt injection in
web pages or PDFs Treat retrieved content as untrusted data; never let
it override system instructions or tool permissions. Cross-tenant data
leakage Tenant-scoped retrieval filters, repository authorization and
tests for isolation. Secret exposure Environment/secret manager,
SecretStr, redaction and no secrets in logs. Unsafe file uploads File
type/size validation, malware scanning policy, isolated parsing and
storage controls. Unrestricted web access / SSRF Allowlisted
schemes/domains where applicable, block private IP ranges and validate
redirects. Excessive tool use or cost Per-run budgets, rate limits,
timeouts, max iterations and concurrency limits. Sensitive research
content Retention policy, access controls, encryption in transit and at
rest. Unsafe report rendering Escape untrusted text and sanitize
generated HTML/Markdown where rendered. 8.2 Reliability patterns ●
Timeouts on every network and model call. ● Bounded retries with
exponential backoff and jitter for transient failures. ● Circuit
breakers or provider fallback for repeated upstream failures. ●
Idempotent ingestion and task execution. ● Checkpointing and resumable
workflow execution. ● Dead-letter handling for jobs that repeatedly
fail. ● Graceful partial completion when a non-critical source or agent
fails. ● Explicit cancellation and deadline propagation. 8.3 Source
quality and research governance ● Classify sources by type and
provenance; do not treat all sources as equally authoritative. ● Record
publication date and retrieval date separately. ● Prefer primary sources
for regulations, official statistics and original research when
available. ● Flag paywalled, inaccessible, undated or secondary sources.
● Preserve contradictory evidence and describe why sources differ. ●
Avoid presenting an agent’s confidence score as a calibrated statistical
confidence. ● Make research limitations visible in the final report.

Complete phase-wise implementation roadmap The roadmap is ordered to
reduce rework. Each phase has a clear deliverable and exit criteria. The
project should not advance just because code exists; it should advance
when the phase is testable and its key assumptions are validated. Phase
Focus Main deliverable 1 Project bootstrap Runnable FastAPI application,

before proving retrieval and evidence quality.

Common failure modes to avoid ● Too many agents: parallelism creates
overhead, duplicated searches and inconsistent outputs. ● Unbounded
loops: critic and verifier should have explicit retry and cost budgets.
● Unstructured state: large prose blobs make merging, testing and
recovery difficult. ● Citation afterthought: source IDs and locators
must be captured during retrieval. ● False confidence: model
self-reported confidence is not a calibrated probability. ● Retrieval
without evaluation: embedding similarity alone does not prove relevance.

vector collections. ● Prompt-injection exposure: source content must
never be trusted as system instructions. ● Silent partial failure:
missing sources or failed agents must appear in run status and report
limitations.
